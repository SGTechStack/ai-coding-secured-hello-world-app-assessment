# Map: Secured Login App

Label: `wayfinder:map`
Effort: `secured-login-app`
Tickets: [`issues/`](issues/)

## Destination

A **locked plan** for the PRD's username/password auth app (React SPA + Spring Boot, session-cookie auth): every non-obvious decision resolved, so `/do-work` can build it to Appfw Standalone-Login conformance without stopping to decide anything. The map is done when no ticket remains and [17 — Handoff to delivery pipeline](issues/17-handoff-to-delivery-pipeline.md) has handed the plan to `stories-to-issues` → `/do-work`.

Planning only. This map resolves decisions; it does not build the app.

## Notes

**Domain.** Secure username/password login: registration, login, lockout, IP throttling, logout, protected greeting, password reset, admin user management, admin bootstrap. See [`prd/assessment-prd.md`](../../prd/assessment-prd.md) for the 12 stories, NFRs, data model and testing requirements.

**Authority order.** Settled while charting:

1. The Appfw standards in [`App-Standards/`](../../App-Standards/) **win wherever both they and the PRD speak.** Consequences already known: roles become `USER`/`USER_MANAGER` (not `ADMIN`) — **settled in 03**, together with single-role-per-user and a validated `String` in place of the PRD's Java `enum`; hard delete becomes a tombstone with a retention period; password history enters scope.
2. The PRD's **explicit** exclusions hold: JWT, MFA, real SMTP, containerization/CI-CD/hosting, local HTTPS, fine-grained per-resource authz. The last is compatible with the standard, which permits omitting privileges (`Standalone_User_Access_Control_Application_Standard_Questions.md:485`).
3. Standard-only **subsystems** that serve no PRD story are out of scope — see [Out of scope](#out-of-scope).

**Binding standards set.**

- All of [`Appfw-User-Standards/User_Standalone/`](../../App-Standards/Appfw-User-Standards/User_Standalone/) — the 670-line standard, its 760-line question set, and all four Standalone recipes except scheduled hygiene jobs.
- [`Appfw-User-Standards/Shared_Recipes/`](../../App-Standards/Appfw-User-Standards/Shared_Recipes/): Security Headers & SPA CSRF Configuration, Role-Based Access Control Configuration, Secure Self-Read User Endpoint. **Not** Automatic DB Role Synchronization & Deleted Role Backups.
- All of [`Appfw-Logging-Standards/`](../../App-Standards/Appfw-Logging-Standards/) (7,169 lines). **05 read all of it**; its Answer is the de-duplicated applicable set, and the two recipes 05's brief did not name — `Custom_Structured_Log_Encoder.md` and `Logging_Exceptions_With_Enhanced_Details.md` — were covered too. `Recipes/Logging_Batch_And_Scheduled_Jobs.md` is **vacuous for jobs we author**, which is 05's call as **narrowed by 02**. Its gates are Spring Batch on the classpath and `@Scheduled`; the first does not hold, but the second now does — **02** found that Spring Session JDBC ships a framework-internal expired-session sweep (`spring.session.jdbc.cleanup-cron`), kept rather than disabled, and ruled outside the recipe's subject because we neither write it nor log from it. Note how cheaply the gate trips regardless: `@Scheduled` needs no dependency at all, so adding an expired-token sweep of our own would activate all 1,254 lines. Treat that as a scope change, not an implementation detail.
- **The recipes are guides; the standard is the clause list.** 05's most consequential finding, and it governs how every remaining logging ticket reads its sources: normative force lives in `Structured_Logging_Application_Standard.md` (`MUST`, `[Enforced Constraint]`), not in the recipes. So a requirement with no recipe template is still mandatory, and a recipe's enthusiasm is not a mandate.

**Nuance, recorded so it isn't re-litigated.** `Questions.md:431` ("Roles cannot be created or modified through API endpoints") constrains *defining* roles, not *assigning* them. PRD Story 10 (admin changes a user's role) survives intact.

**Skills every session should consult.** `grilling` and `domain-modeling` by default. `policies` / `spec-compliance` when checking a decision against Appfw or IM8. The Appfw question set is a pre-written decision frontier — consult it rather than re-deriving questions.

**Branch.** `taniakoh`. Per [`README.md:33`](../../README.md) nothing may be committed to `main`.

**Standards repo.** [`App-Standards/`](../../App-Standards/) is a **git submodule** pinned at `ff5ab8205fdfb641210164eeaa2365e48e04846b` — **settled in 06**, which also found that this assessment repo is **public** while the standards upstream is **private**, so the standards must never be vendored as plain files here. Clone with `git clone --recurse-submodules`, or run `git submodule update --init`; without it every citation below points at an empty directory. Citations are `path:line` against that pin, so **re-pinning the submodule invalidates line numbers map-wide** — treat a bump as a map-level event.

## Decisions so far

<!-- one line per closed ticket: gist + link. Zoom the link for the detail. -->

- [01 — Context, topology and API surface](issues/01-context-topology-and-api-surface.md): Internal-enterprise, single-instance (JDBC session store regardless); base path `/api/v1` externalized as `api.base-path`; **JSON-only login** at `POST /api/v1/auth/login` via a custom filter subclassing `UsernamePasswordAuthenticationFilter`; admin endpoints are **resource-oriented** `/api/v1/users/**` guarded by role, so the PRD's `/api/admin/**` prefix is gone; an `/auth` segment holds login, logout and the endpoints the standard names no path for (register, password-reset); full endpoint inventory in the ticket.

- [03 — Role model reconciliation](issues/03-role-model-reconciliation.md): `ADMIN` becomes **`USER_MANAGER`** (a pure rename) and no third role exists; **one role per user**, a scalar `NOT NULL` `users.role`, with `role-hierarchy: "ROLE_USER_MANAGER > ROLE_USER"` supplying an admin's baseline user access; registration hard-codes `USER` while `POST /users` lets a manager choose; role definitions live in `application.yml` **and** a minimal read-only `roles` table keyed by name; guards key on role authorities with **no privilege layer**; `GET /api/v1/roles` is added to 01's inventory; every self-action on `/users/{userId}` is rejected `403` and the app must always retain at least one enabled `USER_MANAGER` (`409` otherwise).

- [05 — Which logging standards actually bind a two-process app](issues/05-logging-standards-applicability.md): The recipes are guides; `Structured_Logging_Application_Standard.md` is the clause list, so **a mandatory event with no recipe template is still mandatory** and the audit surface is ~2.5× the PRD's list. Ten `[Enforced Constraint]`s bind (`:319-330`) — including **Micrometer Tracing on the classpath** (`:321`), which settles this ticket's key question: `trace.id`/`span.id` are required on **every** line even with one service, but **no exporter, collector or trace platform is needed** (`Trace:14`), so the feared collision with the hosting exclusion does not arise and the SPA need send nothing. Also mandatory: an MDC filter clearing in `finally`, a global exception handler, boundary masking (three permitted mechanisms), and a **separate audit appender**. A typed audit module is **recommended, not mandatory**; "plaintext password never logged" is satisfied by **prevention, not masking**; retention TTL is the integrator's, not the app's. The batch recipe (1,254 lines) is **confirmed vacuous** — **narrowed by 02** to *vacuous for authored jobs*: Spring Session JDBC ships one framework-internal `@Scheduled` sweep, which is outside the recipe's subject. Three hard schema gaps land on 12: **no target/resource field exists**, `event.action`'s closed enum has **no** role-change or status-change value (invalidating one of 01's stated rationales, not its decision), and an unknown-username failure has **`trace.id` as its only permitted subject field**. Two decisions split off as 18 and 19; five tickets amended. Full cites in the ticket; detail in [`research/`](research/).

- [02 — Persistence and session backend](issues/02-persistence-and-session-backend.md): `Q6` answered **PostgreSQL as the declared target**, H2 confined to `dev` (file-based, so Story 12's no-duplicate-admin branch is actually observable) and `test` (in-memory), both in `MODE=PostgreSQL`; `Q7` answered **Spring Session JDBC on the shared datasource**. Schema is managed by **Liquibase** with `ddl-auto: validate` — chosen because `Q3`'s admin-bootstrap options are already written as Liquibase changesets — organised as a master changelog including one versioned file per logical change, each downstream ticket owning its own file. Liquibase owns **every** table including `SPRING_SESSION`, via `sqlFile` against Spring Session's *packaged* per-vendor script under `dbms` guards; the recipe's literal `initialize-schema: always` (`Standalone_Privileged_User_Administration_and_Password_Reset.md:378`) **cannot be copied** — it re-runs `CREATE TABLE` every boot and breaks on the second boot of the file-based dev H2. PKs are `UUID` declared abstractly; all timestamps are `TIMESTAMP WITH TIME ZONE` stored UTC, which keeps 05's UTC+8 pin confined to log rendering. Account-lockout counters stay in `users`; **IP-throttle counters are in-memory** and explicitly neither restart-durable nor multi-instance-safe. Portability is discharged by a **Testcontainers PostgreSQL run** handed to 14, reading the PRD's containerization exclusion as covering deployment packaging, not test infrastructure. **One correction:** Spring Session JDBC ships a `@Scheduled` cleanup sweep (`spring.session.jdbc.cleanup-cron`), so 05's "batch recipe confirmed vacuous" is narrowed to *vacuous for authored jobs* — kept rather than disabled, since disabling it would leave the session table unbounded.

- [18 — Client IP in logs](issues/18-client-ip-in-logs.md): `source.ip` is logged **in cleartext**, on **six** security-event classes only (authN success/failure, lockout, logout, authorisation denial, IP-throttle rejection), sourced **solely** from `getRemoteAddr()` / `WebAuthenticationDetails.getRemoteAddress()` with `X-Forwarded-For` rejected outright, stored **verbatim** (no IPv6 normalization), and **omitted** rather than sentinelled where there is no request context. It appears on **no** request-lifecycle line and **never enters MDC** — the scope split that lets `Std:52`/`:359` and `MDC:94`/`:98` all be followed while the recipe mandate is also met. **The ticket's own framing was wrong and the correction changed the answer:** only **four** of the AuthN recipe's templated events carry `source.ip`, not all nine — authorisation denial, session, MFA and authz-success templates omit it, and `AuthN:490` narrows the mandate to "authentication and logout events" — while `Typed:150`/`:189` contradict that recipe outright. Since `Std:255` never names client IP, **the standard mandates `source.ip` nowhere**; the mandate is recipe-level, so the six-event scope is a deliberate choice, not an inherited clause. `Std:230` is recorded as an **interpretation** (the roll-up of the scoped `:52`/`:359`) with the literal reading written down beside it and rejected because it would make `Std:249`'s own brute-force audit mandate unsatisfiable; **four genuine deviations** are recorded unhedged. `Std:236`/`:278`'s mask-or-hash hatch is **unused, not declined** — HMAC was rejected because a system-wide key either never rotates or severs the correlation the field exists for. The record lands as the repo's **first ADR** in a new `docs/adr/`, content specified but the file left for 15; the `X-Forwarded-For` **expiry** (any proxy silently collapses throttle and audit trail to one bucket) goes to 15's deployment assumptions. Two citation corrections: hashed PII is `Std:278` not `:276`; the resource clause is `Std:255` not 12's `:257`.

- [15 — Tech baseline and module structure](issues/15-tech-baseline-and-module-structure.md): **Java 21 / Spring Boot 4.0.x / Spring Security 7.0.x / Maven** — the pin is the standards', not ours: all eight binding recipes state Boot 4.x with Security 7.x and three name Java 21/25, while the standard's "Spring Boot 3.4+ fluent API" (`:299`) is a **floor, not a ceiling**, so the apparent contradiction dissolves. **A correction to the ticket's premise:** §4 Separation of Concerns (`:411-417`) prescribes *endpoint* boundaries, **not** a package layout — the layout is a free choice, and the frontend is wholly unconstrained (zero frontend hits across every binding recipe; the only Appfw frontend standard is MFA's, already out of scope). One repo, sibling `backend/` + `frontend/` (their separate origins are a PRD fact, not a preference); **feature-first** packages under `com.assessment.auth` chosen so concurrently-generated tickets don't collide, with `audit/` a single logging owner and `common/` holding the mandatory global exception handler and MDC filter. Frontend is **Vite + React 19 + TS + react-router v7 + axios**, axios specifically because `:437` requires a global `401/403` logout interceptor. Tracing starter is **OpenTelemetry**, which defaults to the W3C propagation the standard names (`:277`) where Zipkin would need an override. **Secrets are environment variables with no committed defaults**, so a missing `APP_ADMIN_PASSWORD` fails startup rather than seeding a guessable admin. `logback-spring.xml` is mandatory but minimal — two appenders, format always read from `CONSOLE_LOG_STRUCTURED_FORMAT`/`FILE_LOG_STRUCTURED_FORMAT`, audit bound **by logger name not marker** so a static rule can enforce it; `service.version` is stamped by Maven's `build-info` goal rather than typed; `TZ=Asia/Singapore` is pinned explicitly and the rolling local JSON file is taken. **Four ArchUnit rows**, the load-bearing one banning `@Async` and `@Scheduled` under `com.assessment.auth` — the tripwire that keeps 05's 1,254-line batch recipe from activating by accident. `dependency-check-maven` wired in a profile with the *schedule* left to the integrator. Amends 07, 09, 12, 14, 16, 19, 17.

- [19 — Structured log format and the custom encoder](issues/19-log-format-and-custom-encoder.md): **ECS**, via Spring Boot's **native** `logging.structured.format.*`, and the **custom encoder is built** — but on a justification the ticket never named and with a compelled deviation from its recipe. **Three of the ticket's premises were wrong, and two corrections changed the answer.** The feared runtime crash is real but only for *dotted* keys, while `Std:188` mandates the underscore form that writes safely with **no encoder** — so no error path depended on this choice and the move was never forced. Trap 2 is far worse than framed: **all three** AuthN security-event templates (lockout `ERROR`/423, auth failure `WARN`/401, authz denial `WARN`/403 — `AuthN:76-87`, `:89-101`, `:438-449`) carry the error triplet and **none** attaches a throwable, so the recipe's encoder would silently delete **nine fields across the three events at the centre of the audit trail**. That strip-without-inject **violates `Std:167`** ("MUST NOT suppress or drop it silently"), so the deviation is compelled, not chosen: **when no `error` object exists the encoder CREATES it** rather than stripping — schema-valid per `Log_Schema.md:301-306`. Trap 1 **dissolves**: `Trace:912` already shows the correct `<format>${FILE_LOG_STRUCTURED_FORMAT:-ecs}</format>`, so `Encoder:389` is one recipe's defect, not a standards conflict. **The encoder's real justification is masking, not nesting:** `Std:328` is an `[Enforced Constraint]` whose only mechanism available under this route is an encoder extension, so one artifact discharges both `:328` and `:186`. ECS wins because non-ECS dodges a problem confined to three error fields by breaking **eight** named ★ fields (`Log_Schema.md:40-52`); GELF appears **once** in 7,169 lines and `Questions.md` never mentions the format at all. Third-party `logback-ecs-encoder` rejected — it bypasses the very Spring variables `:320` mandates. **`ErrorCategoryResolver` dropped** (~115 lines): `Encoder:334` fires it only when a throwable exists, so it would never run for any of our three key events. **Correction to 15: three appenders, not two** — `:275`'s durable buffer and `:327`'s separate audit destination are distinct clauses, and conflating them leaves application logs with no durable file at all. No ADR, deliberately: this deviates from a *recipe* in the direction the standard commands.

- [06 — How `App-Standards/` is tracked](issues/06-standards-repo-checkin.md): Tracked as a **proper git submodule** pinned at `ff5ab820`, `.gitmodules` written, nested repo left intact and staged but **not committed**. **The deciding fact was outside the ticket's three options:** the assessment repo answers **200** unauthenticated while `SGTechStack/App-Standards` answers **404**, so vendoring the standards as plain files is a **disclosure of a private repo into a public one**, not merely a large diff — and `samuelwong` has already pushed exactly that. Two sibling branches (`mingliang`, `copilot/perform-security-assessment`) hold the *same* gitlink at the *same* commit but **no `.gitmodules`** — the accidental-submodule state that clones as an empty directory; our answer finishes their choice rather than departing from it. Eight of eleven branches track it nowhere, which is why the citations resolve only here. Pin verified against the two `[Enforced Constraint]` lines 03 relies on (`Standalone_User_Access_Control_Application_Standard.md:407`, `:415`). The clone step goes to **17**; the untracked agent tooling (`.agents/`, `agent/`, `.claude/`, `skills-lock.json`, and the still-absent `.gitignore`) splits off as **20**.

- [04 — Password policy and history](issues/04-password-policy-and-history.md): `Q12` answered **min 12 / max 72 / no composition rules / full printable ASCII / BCrypt cost 12 / bundled denylist**; `Q13` answered **history 3 previous + current = four blocked values, and no password expiry at all**. Three of those overturn a recipe. **Max length is 72 because BCrypt in the pinned Spring Security 7.0.6 *throws* above 72 bytes** (verified in the jar), so `Questions.md:296`'s recommended 128 and the recipe's 1024 both turn a long passphrase into a `500`; the ASCII-only charset then makes a 72-*character* cap an exact byte cap. **Composition rules are dropped** — `Privileged:106`'s regex is recipe-only, the standard's one-of-each-class clause (`:357-362`) is scoped to the *admin-generated* password, and the recipe's own note says to remove it; the `\S+$` no-whitespace rule went too, since it bans passphrases. **`3` means three *previous* plus current**, the literal reading of `Standard:355`, which makes **the recipe's own verification procedure (`Self-Service:269-272`) wrong for us** — 14 must not copy it. HIBP is **declined, not skipped**: a variable-latency third-party call on the registration path undermines `Standard:247`'s identical-timing clause. Both scoping questions resolved **in**: self-service change (one endpoint, not a rule-3 subsystem, and the only landing pad forced change has) and the forced-change flag + filter — **but the 30-day grace period is out**, because auto-disable needs a sweep and 15's ArchUnit rule bans `@Scheduled`. Enforcement is an explicit `PasswordPolicy` + `PasswordHistoryService` called by all four write paths, not Bean Validation — which also sidesteps 05's unresolved `ERROR`-vs-`WARN` conflict. `Standard:110`'s specific error and `:247`'s identical responses **do not conflict**: `:247` scopes itself to authentication outcomes. Filter allowlist adds **logout** to the privileged recipe's three paths (without it a flagged user cannot end their own session), and **reset-confirm clears the flag** — the reset endpoints are public so the filter never sees them, and without the clear that user is trapped permanently. Change endpoint takes `{currentPassword, newPassword}` (`:129`/`:240` make current mandatory, against the recipe's DTO), kills **all** sessions including the caller's, invalidates pending reset tokens, and adds a `sendPasswordChangedEmail` stub the PRD never anticipated. Amends 08, 10, 11, 12, 14, 16.

Waits on the self-read path/payload ruling in 10. 01 already fixed the bootstrap sequence: `GET /csrf` → `POST /auth/login` (200, empty body) → `GET /currentUser`; 03 fixed the role vocabulary it will hold (`USER` / `USER_MANAGER`, exactly one) and gave the role-change control a source in `GET /api/v1/roles`.

## Out of scope

<!-- ruled beyond the destination. Never graduates; returns only as a fresh effort. -->

- **JWT implementation** — PRD: design documented in its appendix only.
- **MFA / 2FA** — PRD exclusion; `App-Standards/Appfw-Mfa-Standards/` therefore does not apply.
- **Real SMTP / email delivery** — PRD: stubbed `EmailService` that logs.
- **Containerization, CI/CD, hosting infra** — PRD exclusion.
- **Local HTTPS setup** — PRD: documented deployment assumption; local dev over HTTP.
- **Fine-grained privileges model** — PRD excludes granular per-resource authz; the standard permits roles without privileges (`Questions.md:485`). **03 confirmed the consequence:** `url-guards` key directly on `ROLE_USER_MANAGER` / `ROLE_USER`, not on synthesized authorities like `USER_READ`.
- **Scheduled account-hygiene batch jobs** — `Standalone_Scheduled_Account_Hygiene_Jobs.md`; a whole subsystem serving no PRD story. **04 recorded a consequence:** the standard's 30-day **forced-password-change grace period** (`Standalone_User_Access_Control_Application_Standard.md:50`, `:372`) falls out with it, because auto-disabling a non-compliant user needs a scheduled sweep and 15's ArchUnit rule bans `@Scheduled` under `com.assessment.auth`. The `requirePasswordChange` flag and its filter are **in** scope; only their time-expiry is not.
- **Remember-me** — `Questions.md:238`; no PRD story.
- **Admin-created-user activation workflow** — `Questions.md:535`; no PRD story (registration is self-service).
- **Automatic DB role synchronization and deleted-role backups** — `Common_Automatic_Database_Role_Synchronization_and_Deleted_Role_Backups.md`; same shape as the hygiene jobs. **Narrowed by 03:** what is out is the *archive-on-removal* (`DeletedRole`) machinery and the `sync-db-users` reset flag. A minimal read-only `roles` table seeded from config at startup **is in scope** — the standard makes persisting role definitions an enforced constraint (`Standalone_User_Access_Control_Application_Standard.md:407`, `:415`).
- **SSO login** — `Appfw-User-Standards/User_SSO/`; this app is Standalone.
- **Appfw File, Interface/Batch, Report and Mcc standards** — no applicable surface in this app shape.
