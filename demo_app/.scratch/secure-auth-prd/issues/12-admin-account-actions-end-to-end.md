# 12: Admin account actions, end to end

**What to build:** An admin can disable and re-enable, promote and demote, and delete any account except their own. Each change takes effect at once, because the target's existing sessions are ended. The server rejects self-actions even if the UI is bypassed. See spec §Backend modules › Admin module, §Frontend modules › Admin users page, and Acceptance scenarios › Story 7.

**Blocked by:** 09, 11

**Status:** resolved

- [x] `PATCH /api/v1/admin/users/{id}/status` with `{enabled}` → `200` with the updated row. Disabling expires the target's sessions: their live session gets `401` and they can't log in. Re-enabling lets them log in again.
- [x] `PATCH /api/v1/admin/users/{id}/role` with `{role: "USER" | "ADMIN"}` → `200` with the updated row. An unknown role → `400 VALIDATION_FAILED`. A change expires the target's sessions, and the new role applies after they log in again.
- [x] `DELETE /api/v1/admin/users/{id}` → `204`. It expires the target's sessions, their reset tokens cascade, and they can't log in.
- [x] Self disable, self demote and self delete → `409 SELF_ACTION_NOT_ALLOWED`, with state unchanged. An unknown id → `404 USER_NOT_FOUND`. A non-admin → `403`. Anonymous → `401`. Every mutation without CSRF → `403`.
- [x] Audit events `USER_ENABLED`, `USER_DISABLED`, `USER_ROLE_CHANGED` (old and new role), `USER_DELETED` and `ADMIN_SELF_ACTION_REJECTED`, each with actor, target and IP.
- [x] The frontend admin API has `setUserEnabled`, `setUserRole` and `deleteUser`, each invalidating the user list on success.
- [x] Each row has an enable/disable toggle, a role control and a delete button behind a confirmation `AlertDialog`. A failed action shows `ErrorAlert`.
- [x] Frontend tests: each action sends the right request and refreshes the list, delete needs confirmation, and a failure shows the alert.
- [x] e2e Story 7 scenarios 2, 3 and 4 pass under the CSP fixture, using freshly registered users.

## Comments

- **Backend.** `AdminUserController` gained `PATCH /{id}/status` (`StatusChangeRequest {enabled}`, `@NotNull`), `PATCH /{id}/role` (`RoleChangeRequest {role}`) and `DELETE /{id}` (`204`); the signed-in admin (`@AuthenticationPrincipal`) is passed to `AdminUserService` as the actor. `role` is a `String` checked with `@Pattern("USER|ADMIN")` instead of binding to the `Role` enum, so an unknown (or lowercase, or missing) role is `400 VALIDATION_FAILED` with `fieldErrors[role]` rather than Jackson's `400 MALFORMED_REQUEST`. `UserAccount` gained `setEnabled` and `setRole`.
- **Service rules.** Lookup first (`404 USER_NOT_FOUND` "User not found"), then the self check (`409 SELF_ACTION_NOT_ALLOWED` "You can't change your own account.", audited as `ADMIN_SELF_ACTION_REJECTED` with `target` and `action=status|role|delete`). Any self target is refused, including a no-op (self-enable, self-promote). Setting the value an account already has returns `200` with the row but changes nothing: no audit line and no session expiry. Delete uses `accounts.delete`; `password_reset_token.user_id ... ON DELETE CASCADE` (V2) removes the tokens.
- **After commit.** For a real change, `SessionExpiry.expireAllSessionsOf(username)` and the audit line (`USER_ENABLED` / `USER_DISABLED` / `USER_ROLE_CHANGED` with `oldRole`, `newRole` / `USER_DELETED`, each with `target` after the standard `actor`, `ip`, `outcome`) run in a `TransactionSynchronization.afterCommit`, so a login racing the change can't keep a session with the old state, and a rolled-back change is never audited. The class-level `@PreAuthorize("hasRole('ADMIN')")` covers the new methods (`AdminUserServiceSecurityTest` asserts it).
- **Backend tests.** `AdminUserActionsApiTest` (13 cases, fresh target per test, `admin`/`johndoe` never mutated): disable ends the live session (`/me` → `401`) and blocks login, and re-enable restores it; promote/demote ends the old session and applies on re-login; delete removes reset tokens (counted in the table, since no API exposes them) and blocks login; self actions `409` with state unchanged and 3 audit lines; unknown id `404`; `USER` `403`, anonymous `401`, no CSRF `403`, all with state unchanged; audit field order; no-op changes are silent. Refused logins use their own IP. `SpaAuthFlow` gained `userId(mvc, adminSession, username)` and `setEnabled(mvc, username, enabled)`; `LockoutApiTest` and `PasswordResetApiTest` now disable accounts through the admin API instead of raw SQL (`PasswordResetApiTest` still reads token hashes with `JdbcTemplate`). `mvn verify`: 220 tests, JaCoCo met.
- **AlertDialog and the CSP.** The CSP stays strict (`style-src 'self'`, nothing relaxed). Radix `AlertDialog` is not used: it always enables `react-remove-scroll`, whose `react-style-singleton` injects a runtime `<style>` that `style-src 'self'` blocks. `components/ui/alert-dialog.tsx` is a small shadcn-styled `AlertDialog` on the native `<dialog>` opened with `showModal()`: `role="alertdialog"`, `aria-labelledby` (title) and `aria-describedby` (description); the browser makes the page inert, puts focus on the first control (Cancel, first in DOM order), closes on Escape (the `close` event calls `onOpenChange(false)`) and restores focus. Backdrop via Tailwind's `backdrop:` variant; the scroll lock is a stylesheet rule (`body:has(dialog[open]) { overflow: hidden }` in `styles.css`). jsdom lacks `showModal`/`close`, so `src/test/setup.ts` adds a stand-in that toggles `open` and fires `close`. README's CSP section records the choice. The e2e CSP fixture passes on Scenario 4, which opens, cancels and confirms the dialog (and asserts Cancel has focus).
- **Frontend.** `api/admin.ts`: `setUserEnabled(id, enabled)`, `setUserRole(id, role)` (both `PATCH`, resolve to the row), `deleteUser(id)` (`DELETE`), and `useAdminUserAction()`, a mutation that runs one of them and invalidates `["admin","users"]` on success. No CSRF 403 retry for these (the token is fresh after login; a failure shows the alert). `OwnAccountActions` became `RowActions` on every row: the same three buttons in the same order ("Disable"/"Enable", "Make admin"/"Make user", "Delete"), enabled on other rows and disabled while a row action is pending; on the own row they are disabled with the note as their accessible description, as before. Delete opens the dialog ("Delete <username>?", Cancel / Delete, "Deleting..." while pending); the dialog closes on success or failure. A failure sets one page-level `ErrorAlert` above the table ("<username> no longer exists." for `USER_NOT_FOUND`, the own-account note for `SELF_ACTION_NOT_ALLOWED`, else "Unable to change <username>. Please try again later."); the next action clears it. Tests (`AdminUsersPage.test.tsx`, stateful MSW admin API): each action's method/path/body/CSRF header and the list refetch, delete only after confirming, cancel sends nothing, failure alerts, and other rows' controls enabled. `npm run check` green (143 tests).
- **E2E.** `story-7-admin.spec.ts` Scenarios 2–4, each with a freshly registered user (registered through the UI in the test's page, then the admin logs in there). The target user logs in in a second `browser.newContext()` (outside the CSP fixture, like Story 6), so the admin's session stays put: Scenario 2 also shows the target's live session ends on disable; Scenario 3 checks the Admin link appears only after re-login; Scenario 4 cancels once, then confirms, the row disappears, and the deleted user's login is refused. Full suite: 38 passed with `CI=1 BACKEND_PORT=18093 FRONTEND_PORT=13012`; Story 7 passed 3 repeats.
