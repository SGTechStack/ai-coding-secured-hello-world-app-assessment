# CSRF tokens are session-bound and fetched from a bootstrap endpoint

The SPA gets its CSRF token from `GET /api/csrf` and sends it in the `X-CSRF-TOKEN` header, with the token stored in the server-side Session. The common SPA pattern of a JS-readable `XSRF-TOKEN` cookie (`CookieCsrfTokenRepository`) is prohibited by App-Standards, because it weakens a stateful, session-based design. Do not "simplify" to the cookie pattern. For the same reason, logout keeps CSRF protection: logging out on an expired Session returns 401/403, and the SPA handles that by clearing its state and redirecting to login.

A token is reused for the life of a Session and is not single-use per request. We read the Standard's "previously redeemed CSRF tokens are rejected on subsequent attempts" as: a token issued before a login or logout is rejected after it, because Spring issues a new token at both. That is tested. Rotating the token on every request would need a custom repository and would make parallel SPA requests race each other for the current token.

One endpoint is exempt: `POST /api/client-events`, which the SPA uses to report a browser error or a page-load timing (story 111). The logout reasoning above does not transfer, because logout acts *on* a Session while a client event needs none — it is public, changes no Account state, and only moves a Micrometer counter whose tag values are a fixed enum, so a forged report can do nothing a caller could not already do by posting directly. It is rate-limited per client address instead, and the SPA sends it without credentials so no Session is even resolved. The exemption is not a convenience: reporting starts at page load, and with CSRF on, every Visitor and every crawler would fetch a token, `HttpSessionCsrfTokenRepository.saveToken` would call `getSession()`, and the server would persist a Spring Session JDBC row and set a `SESSION` cookie before any interaction — with no cap on anonymous Sessions (the concurrent-Session limit is per Account) and no rate limit on `GET /api/csrf`. Re-adding CSRF to this one endpoint brings that back, so a test asserts that a client event creates no Session and sets no cookie.
