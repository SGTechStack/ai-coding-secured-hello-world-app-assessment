# 15: Admin: delete an Account, with tombstone

**What to build:** An Admin deletes another Account from the admin screen, after confirming. Its Sessions end, its Password History and Reset Tokens go, and a tombstone keeps its UUID, username, email, deletion time and the deleting Admin indefinitely. That username can never be registered or bootstrapped again, though the email can be reused. See the spec's stories 10–11, 71–74 and 81 (the tombstone half), "Account administration service", "Schema" (`deleted_users`), and ADR 0001 (tombstone as soft delete). Use `CONTEXT.md`'s Deleted Account.

**Blocked by:** 09 (delete removes the Account's Reset Tokens), 11 (self-action guard and last-Admin rule)

**Status:** resolved

- [x] A Flyway migration creates `deleted_users` (the deleted Account's UUID, unique username, email, deleted-at, deleting Admin's UUID).
- [x] `DELETE /api/admin/users/{id}` returns 204. In one transaction it writes the tombstone, removes the Account and its `password_reset_tokens` and `password_history` rows, and then ends the Account's Sessions. An unknown id returns 404.
- [x] Deleting your own Account returns 403 `self_action_forbidden`, and deleting the last enabled Admin returns 409 `last_admin` (checked under the same row lock as ticket 11).
- [x] Registration rejects a tombstoned username with 400 `user_exist`, but accepts a Deleted Account's email.
- [x] The Bootstrap Admin initializer fails startup with a clear message when the configured username is tombstoned.
- [x] Audit events: INFO `user-administration` for delete, with `target.user.id` and state; WARN for rejected attempts; `session-end` for the ended Sessions.
- [x] SPA: a delete action on the admin screen that asks for confirmation and shows 403 and 409 errors clearly.
- [x] Tests cover: delete writes the tombstone and ends the target's Sessions; the deleted Account's pending Reset Token no longer works; self-delete gets 403; the last-Admin delete gets 409; a tombstoned username is blocked while the email is reusable; bootstrap startup fails on a tombstoned username; 404 for an unknown id; and the audit events.

### Verification

All eight acceptance criteria met. `DELETE /api/admin/users/{id}` returns 204 and, in one transaction, writes a `deleted_users` tombstone (the Account's UUID as PK, unique username, email, `deleted_at`, `deleted_by`) and removes the Account with its `password_reset_tokens` and `password_history` rows; the target's Sessions end after commit with `session-end` / `event.reason: account_deleted`. An unknown id returns 404 `not_found`, self-delete 403 `self_action_forbidden`, and the last enabled Admin 409 `last_admin`. Registration rejects a tombstoned username with 400 `user_exist` while accepting a Deleted Account's email; the Bootstrap Admin initializer fails startup on a tombstoned username. The SPA gained a per-row delete behind an in-row confirmation showing the 403 and 409 messages. Flyway `V4__deleted_users` exists for H2, PostgreSQL and MySQL.

**Design notes:** the self-action guard and last-Admin rule reuse issue 11's `lockTarget` and `guardLastAdmin` under the same lock set in the same order, so delete introduces no new locking path and no new deadlock shape. The tombstone insert and the Account removal share one transaction, so a concurrent registration sees either the live Account or the tombstone and never neither — no cross-table unique constraint is needed. The tombstone check is folded into the one combined `user_exist` branch, so the response never distinguishes username from email from tombstone. FK ordering is explicit (`accounts.flush()` between the child deletes and `accounts.delete`) rather than relying on Hibernate's action-queue order. No FK on `deleted_by`, since the deleting Admin's own Account may later be deleted; email deliberately not unique. `JpaRepository.save` on a pre-set `@Id` issues a `merge` rather than a `persist` — one extra SELECT on a rare admin action, kept because it also makes a repeat tombstone idempotent rather than throwing.

**Decision taken during review** (recorded in `docs/agents/reviewer-decisions.md`): **a Session could outlive its deleted Account, unrecoverably.** Criterion 2's Session ending is one post-commit sweep over `findByPrincipalName`, and Spring Session JDBC indexes a Session under its principal only when the row is written at response commit — so a target mid-login when the delete ran was absent from that result set and kept a live Session carrying the authorities it was issued, including `ROLE_ADMIN`, which satisfied both the `/api/admin/**` URL rule and `@PreAuthorize("hasRole('ADMIN')")`. The same index timing already affected `ACCOUNT_DISABLED` and `ROLE_CHANGED`; delete was different only in that no operator action could revoke the Session, because the id no longer resolved and a repeat `DELETE` returned 404. Chosen fix (option A): a single Account-existence lookup hoisted **above** `RequiredPasswordChangeFilter`'s `allowed` matcher — deliberately above it, since a check below would have skipped `/me`, `/me/password`, `/logout`, `/csrf` and `/client-events` — which calls the new `SessionControl.endCurrent(ACCOUNT_DELETED, …)` to *end* the Session and then throws `InsufficientAuthenticationException`, letting the chain's existing entry point write the 401. This also repairs the disable and role-change timing window. Rejected: documenting the window per issue 05's expiry-gap precedent (that precedent is about a missing audit event, not live authority no operator can revoke), a `hello`-only re-check, a duplicate sibling filter, and moving the check into `SessionControl.enforceLifetime` (better chain position, but it inverts the account → security package direction and needs a port this repo already rejected once as "more surface").

**Verification steps.** Targeted tests only, by request — the full suite was not run. Backend: `AdminAccountDeleteApiTest` 10/10, `AccountAdministrationServiceConcurrencyTest` 2/2, `BootstrapAdminTest` 12/12, `LoggingApiTest` 9/9, `RequiredPasswordChangeApiTest` 14/14, `SessionLifetimeApiTest` 12/12, `LoginApiTest` 21/21, `PasswordChangeApiTest` 25/25, `AdminAccountListApiTest` 15/15, and a consolidated 31-class run at **332 tests, 0 failures, 0 errors**. Flyway applied H2 V4 cleanly under `ddl-auto=validate`, which also validates the entity against the new table.

Three claims were **mutation-checked by the reviewer rather than trusted**, each restored and re-verified green afterwards. Moving the existence check back below the `allowed` matcher fails *exactly* the `/csrf` test and nothing else, so the placement is genuinely pinned. Removing the `endCurrent` call while keeping the throw fails *both* new tests, so the revoke-not-just-refuse half is pinned too, not merely the 401. Disabling either a11y mechanism fails its own assertion. The new concurrency test is non-vacuous by construction: `containsExactlyInAnyOrder(SUCCEEDED, REJECTED)` fails if both win or both lose, and it also asserts exactly one tombstone, so the loser's rollback left no half-deletion.

**One test fixture changed to accommodate the new invariant**, scrutinised deliberately because that is where a regression can hide: `LoggingApiTest.authenticatedRequestLinesCarryTheAccountUuid` injected a synthetic principal for a UUID with no `users` row and asserted 200, which the new rule forbids. It now inserts a real Account under a *different* username (`loggingfixture`) and removes it in a `finally`. Coverage is preserved exactly — the assertion is `doesNotContain("testuser123")`, the *principal's* username, which is still synthetic and still never stored; reusing `testuser123` as the stored username would have made the test ambiguous about which source it proved. The reviewer independently confirmed no coverage was dropped and that the shared-database window cannot interleave (no Surefire parallelism configured).

Also checked and found safe: hoisting a DB lookup above a bypass matcher is the shape of the recorded `/client-events` resource-exhaustion concern, but the lookup stays behind the `authentication == null` / `AccountIdentified` guard, so an anonymous flood on the `permitAll` paths still performs **zero** queries. Only a cookie-bearing caller pays, and the SPA's telemetry sends `credentials: 'omit'`.

**Contract change, intended:** `POST /api/logout` for a deleted Account now returns 401 rather than 200. Harmless and already specified — `spec.md`'s Logout bullet says logging out on an expired Session returns 401/403 and the SPA treats that as "already logged out", which `api/auth.ts:logout()` implements. The Session is ended by the existence check either way, and the subsequent `refreshCsrfToken()` then arrives unauthenticated, hits `permitAll` and returns 200.

**Known gap, tracked:** `GET /api/csrf` now 401s for a deleted Account where it previously returned 200, and `client.ts`'s `refreshCsrfToken` *throws* on a non-ok response instead of routing a 401 through `onSessionEnded`. So a deleted holder whose very first request on the stale Session is the `/csrf` fetch inside `send()`, with no cached token, gets a rejected promise rather than the clean redirect to login. It needs that exact ordering: the token is cached at login, a page reload issues `GET /me` first (which 401s and redirects correctly), and `endCurrent` fires on the first request reaching the filter, so `/csrf` answers 200 from then on. The defect is general rather than delete-specific — any future per-request revocation check reaches the same path — so per the issue-18 precedent it gets a tracked owner instead of a patch to the one instance: **issue 19** (`19-csrf-refresh-401-session-end.md`, needs-triage).

**Known gap, accepted:** `deleted_users` retains username and email indefinitely with no purge path. This is exactly what ADR 0001 decided, but it makes the table the repo's only indefinite PII store, which is worth naming rather than leaving implicit.
