# 14: Operations: metrics and dependency scan

**What to build:** An operator can watch request latency, traffic, errors and saturation on a management port that isn't publicly reachable, and can run a dependency scan that fails on critical CVEs. See the spec's story 111, "Security configuration" (metrics), "Repository and stack", and "Testing Decisions" (dependency scan). The README deployment notes are ticket 16.

**Blocked by:** 01

**Status:** resolved

- [x] Spring Boot Actuator runs on a separate, configurable management port and exposes only `health` (status only, no details) and `prometheus`. The metrics include `http.server.requests` (latency, traffic, errors), JVM metrics, and connection-pool saturation.
- [x] The API port serves no Actuator endpoints, and the API's filter chain and public paths are unchanged.
- [x] A Maven `security` profile runs OWASP Dependency-Check (`mvn -P security verify`) and fails the build on critical CVEs. The SPA's npm tree is scanned the same way, by `npm run security` in `frontend/` (`npm audit --audit-level=critical`). Widened past the spec's backend-only wording during implementation, because a critical CVE in a shipped SPA dependency is the same risk and the check was already free. No root-level orchestration of the two commands: that belongs to issue 16.
- [x] The SPA reports client-side errors (including those caught by the app's `ErrorBoundary`) and basic performance data to an operator-visible destination, without sending user data or error details beyond what is needed. The mechanism is decided when this issue is picked up. (Added from the issue 01 IM8 lm-16 gate finding; see `docs/agents/reviewer-decisions.md`.)
- [x] Tests cover: Actuator endpoints are absent from the API port; `health` on the management port returns status only; and `prometheus` exposes `http.server.requests` after a request.

## Comments

### Verification (2026-09-30)

**Implemented:** Actuator runs on a separate, configurable `management.server.port` (9090), bound to `127.0.0.1` by default so "not publicly reachable" is enforced by configuration rather than only by prose. `management.endpoints.access.default=none` with explicit `read-only` for `health` and `prometheus`, `web.discovery.enabled=false`, health `show-details`/`show-components=never`, and `health.probes.enabled=false` (Boot 4.1 enables liveness/readiness by default, which made `health` answer `{"groups":[…],"status":"UP"}` and served two extra paths, against "status only"). `percentiles-histogram.http.server.requests=true` gives latency buckets.

`ManagementSecurityConfig` adds a `SecurityFilterChain` at `@Order(5)` whose `securityMatcher` matches only requests whose local port equals `local.management.port` **and** differs from `local.server.port`. Boot 4.1 does route management-port requests through the parent `FilterChainProxy`, so without this the API chain's `anyRequest().denyAll()` returned 401 for `health` and `prometheus`. Scoping by port rather than by `EndpointRequest.toAnyEndpoint()` leaves the API port literally unchanged: `/actuator/**` there is still refused by default-deny. The matcher fails safe — it returns false when `local.management.port` is absent (every MockMvc test) or equals `local.server.port`, so it can never widen the API port.

A Maven `security` profile runs `dependency-check-maven` 13.0.0 at `verify` with `failBuildOnCVSS=9` (CVSS v3 Critical), `skipTestScope=true`, `nvdValidForHours=24`, the key read via `nvdApiKeyEnvironmentVariable=NVD_API_KEY` so it never becomes a Maven property that debug logging could print (GHSA-qqhq-8r2c-c3f5), and `backend/dependency-check-suppressions.xml` (empty, commented) so the first false positive has a documented escape hatch. Criterion 3 was widened to cover the SPA's npm tree via `npm run security` in `frontend/`.

Criterion 4's mechanism (the issue left it open): the SPA's CSP `connect-src` allows only the API origin, so the API is the only reachable operator-visible destination. `POST /api/client-events` is public, rate-limited 60/min per direct client address, and structurally unable to carry user data or error detail — a fixed `ClientEventKind` enum, a `path` constrained to `/[A-Za-z0-9/_-]{0,63}` (no query string or fragment, which is where the Reset Token travels), an optional `durationMs` bounded to 0…3_600_000, and a record-level `@AssertTrue` enforcing "duration iff timed kind". There is no field for a message, stack trace or identifier. Reports land as `app.client.errors{kind}` plus a WARN application-log line, and `app.client.performance{kind}` plus DEBUG. Meters are tagged only by the enum, so a client cannot inflate metric cardinality. `frontend/src/api/telemetry.ts` is wired from `main.tsx` (window `error` / `unhandledrejection` and Navigation Timing) and `ErrorBoundary.componentDidCatch`; reports are best-effort and capped at 10 errors per loaded page.

**Deviations and decisions** (all six recorded in `docs/agents/reviewer-decisions.md`):

- **`POST /api/client-events` is exempt from CSRF — the one exemption from ADR 0002, amended there.** With CSRF on, `startClientReporting()` at module scope made every page load call `ensureCsrfToken()` → `GET /api/csrf`, and `HttpSessionCsrfTokenRepository.saveToken` calls `request.getSession()`. Every Visitor and crawler got a persisted `SPRING_SESSION` row and a `SESSION` cookie before any interaction, with no cap on anonymous Sessions (issue 05's cap is per Account) and no rate limit on `GET /api/csrf`. ADR 0002's logout reasoning does not transfer: logout acts *on* a Session, a client event needs none. `telemetry.ts` therefore bypasses `apiRequest` entirely and sends a plain `fetch` with `credentials: 'omit'`, which is stronger than skipping the token — no cookie is sent, so no Session is resolved and a report can never be tied to an Account. Three tests hold the invariant, including that no `GET /csrf` is made at all.
- **Criterion 3 is verified by configuration, not by execution.** See the open item below.
- **`POST /client-events` joined `RequiredPasswordChangeFilter`'s allowlist**, which widens no authorization since the path is already `permitAll`. It was approved to stop per-page-load audit noise, but the CSRF exemption eliminated that cause in the same pass: the SPA's reports are anonymous, so `doFilterInternal`'s first branch short-circuits before the allowlist is consulted. The entry stands as defence in depth for a caller that does send a cookie, and its test posts one explicitly, so it is genuinely covered rather than vacuous.
- **`CONTEXT.md` gains one `Client Event` term** under a new "Operations" heading, carrying the payload constraint, because the constraint *is* the security control and a code comment would not stop a later change adding a message field. No management-port term (configuration, not vocabulary). No new ADR: the only ADR change is the 0002 amendment.
- **The management port matcher reads the port per request and must not be cached.** A memoized version was implemented and reverted: 17 of 23 `ManagementEndpointsTest` assertions failed because a cached value pointed at a port nothing serves, and the live management port then fell through to the API chain's default-deny. Instrumented with `identityHashCode`, one matcher and one `Environment` saw `liveApi` unchanged while the management port moved (58613 → 58620), so the port does change during a single context's life under `management.server.port=0`; the trigger was not isolated and the javadoc does not claim one. Caching also buys nothing — an API-port request costs one property lookup and returns at the first check, and the second lookup only runs for management-port traffic, a few scrapes a minute.

**Fixed on the way (pre-existing bug):** the Actuator child context's `ContextClosedEvent` propagates to the parent, so `ApplicationLifecycleLogger` wrote "Application stopping" and the `application-shutdown` audit event twice. It now ignores events from any context but its own, and `AuditLogTest` asserts exactly one `application-shutdown` event.

**Open item for handoff (not done here):** `mvn -P security verify` was **not** proven by execution. dependency-check 13 cannot update its NVD data without an API key and aborts the build rather than reporting a clean result (`NvdApiException: Invalid API Key, length of 0`) — correct fail-closed behaviour, but this environment has no key and obtaining one is a human-only step. The profile was verified by `./mvnw -P security help:active-profiles` and `help:effective-pom` (profile activates, `dependency-check:check` bound to `verify`, `failBuildOnCVSS=9`, suppression file wired). **A human must run `NVD_API_KEY=… ./mvnw -P security verify` before handoff**, as the spec requires the scan to be run. `npm run security` *was* run: `found 0 vulnerabilities`.

**Known gaps, accepted:**

- **The rate limiter is acquired after `@Valid`**, so a malformed body is rejected and `GlobalExceptionHandler.auditInputFailure` writes an `ACCESS_CONTROL` `validation` audit event before the limiter runs — an unrated audit-log write. Pre-existing and shared with `/register` and `/password-reset/*` (`IpThrottle` is login-only), but the CSRF exemption removed the token bootstrap that previously made it cost something, so a bare malformed POST is now free, and `/client-events` is the only one of the three a browser calls unprompted. Tracked as **issue 18**, covering all three endpoints under one mechanism rather than fixing only this one.
- **Telemetry fails silently if `app.cors.allowed-origins` is wrong.** A failed report is deliberately swallowed so it cannot become an error of its own, so there is no operator-visible signal that client reporting has stopped — the absence of the `app_client_*` series is the only clue.
- **`errorReportsSent` is module state**, so "10 reports per loaded page" is really per tab lifetime under client-side routing: after 10 errors a long-lived tab goes permanently silent, and a failed send still consumes budget.
- **`telemetry.ts` duplicates `API_BASE` from `client.ts`** — two sources of truth for the API origin, the price of bypassing `apiRequest`. Cosmetic; worth a shared constant if it drifts.
- **`app.rate-limit.client-events.*` is absent from the `Application started` config line**, consistent with the reset limiters but not with login and registration. Cosmetic.
- **Pre-existing test-infrastructure fragility, newly diagnosed:** `LogCapture` reads real log files at the fixed `target/test-logs` path, so two builds running concurrently in one working tree read each other's lines. This surfaced as two unrelated failures (`BootstrapAdminTest`, `LoginApiTest`) whose captured lines carried two different `pid` values interleaved in one assertion window. A clean sequential run is green. It affects any test asserting on log contents — the whole Seam 4 approach. A per-JVM subdirectory under `app.logging.directory` would fix it; not attempted here.
