# 16: README deployment notes

**What to build:** An operator preparing a real deployment reads the README and learns everything they must add around the app, and every Standard or IM8 deviation they are accepting. It documents the app as built, which is why it comes last. See the spec's Further Notes deployment checklist, "Security configuration" (TLS, secrets, metrics), and ADR 0001's acknowledged and accepted deviations.

**Blocked by:** 07 (IP-hash HMAC key), 13 (Bootstrap Admin's required first-login change), 14 (management port)

**Status:** resolved

- [x] The README covers:
  - TLS 1.2+ outside `dev`, including to the database.
  - The single-instance requirement.
  - A secrets manager for the Bootstrap Admin password, HMAC key and datasource credentials, with HMAC key rotation.
  - The Bootstrap Admin's first-login change, and that the `dev` fallback must never be used outside local development.
  - Forwarding the audit file to central logging with at least 90 days' retention, write-once storage, restricted access, and alerting when audit events stop.
  - The headers the SPA host must send, and setting `VITE_SECURITY_CONTACT`.
  - Never routing the management port publicly.
  - The production CORS allowlist, and reverse-proxy and NAT caveats for the IP Throttle.
  - The IM8 deviations accepted for this reference implementation.
- [x] The Postgres and MySQL Flyway migrations (`db/migration/postgresql`, `db/migration/mysql`) are run against real Postgres and MySQL databases, with Hibernate `ddl-auto=validate` passing. Until now only H2 has been tested (reviewer decision "Non-H2 migrations", issue 03).
- [x] Every configuration property the README names matches the property the app actually reads, and following the README from a clean checkout starts both applications in `dev`.

### Verification

All three acceptance criteria met. The README is now an operator-facing deployment document: an overview and doc map, repo layout, requirements, the `dev` quick start, tests, a configuration reference table, a ten-section **Deploying outside `dev`** guide, a condensed deployment checklist, and an **Accepted deviations** section carrying the IM8 table (ac-2, ac-3, ac-4, ac-7, ac-8, ac-12, lm-18) with what mitigates each. All nine criterion-1 bullets are present as their own numbered sections with concrete property and header values rather than advice: TLS 1.2+ including to the database (`sslmode=verify-full` / `sslMode=VERIFY_IDENTITY`); the single-instance requirement the in-memory rate limits impose; a secrets manager for the Bootstrap Admin password, HMAC key and datasource credentials, with the correlation cost of rotating the HMAC key; the Bootstrap Admin's first-login change plus an explicit warning that the `dev` fallback `admin`/`password` must never be used outside local development; audit forwarding with at least 90 days' retention, write-once storage, restricted access and alerting when events stop; the header set the SPA host must send plus `VITE_SECURITY_CONTACT` and the `security.txt` `Expires` date; never routing the management port publicly, including the loopback-binding trade-off; and the production CORS allowlist with its reverse-proxy and corporate-NAT caveats for the IP Throttle.

**A real defect was found by criterion 2, not merely documented.** Flyway 10 moved per-vendor support out of `flyway-core`, and the backend carried neither the vendor modules nor the Postgres/MySQL JDBC drivers, so the app could not run its own Postgres or MySQL migrations at all (`FlywayException: Unsupported Database: MySQL 8.0`) and could not connect to the vendor the README names as the production target. Only H2 had ever been exercised, so nothing caught it. Fixed by shipping `flyway-database-postgresql`, `flyway-mysql`, `postgresql` and `mysql-connector-j` at `runtime` scope, all Boot-managed and unpinned. This discharges the "Non-H2 migrations: fix obvious dialect issues now, defer real-database runs" decision from issue 03, which deferred the real-database run to the issue that owns deployment — no new decision was needed.

**Design notes.** `NonH2MigrationTest` boots the whole app against a real Postgres and a real MySQL, so Flyway applies the vendor migration set and `ddl-auto=validate` gates the schema against the entities during context start; context start *is* the assertion. It then asserts four applied migrations and that the Bootstrap Admin row round-trips, which is what proves the UUID primary key (`uuid` on Postgres, `binary(16)` on MySQL). No profile is active, so it also exercises the production configuration rules. Because it needs a Docker daemon it sits behind an opt-in `migrations` profile with a `maven-compiler-plugin` `testExcludes` entry, mirroring the existing `security` profile's precedent, so an ordinary `mvn verify` compiles nothing new and downloads no Testcontainers dependency. The reviewer confirmed the exclusion is airtight against the stale-class hazard: a default `test-compile` after a `-P migrations` run removes the class from `target/test-classes`, so an ordinary `./mvnw test` cannot pick up the Docker-dependent test. Assertions go through `JdbcTemplate` against `flyway_schema_history` and `users` only, rather than inspecting Flyway or Hibernate internals.

**Two documented claims were corrected rather than asserted**, both originally wrong in the direction of being too permissive.

The **Node floor** is now `22.22.2+, 24.15+ or 26+`. The first draft said "20 or later"; the reviewer's proposed replacement of `22.12` was *also* wrong. The range was computed, not guessed: a script walked the whole installed `frontend/node_modules` tree, collected all **76** packages declaring `engines.node` including transitives, and tested candidates with npm's bundled `semver`. The reviewer reproduced the sweep independently and every verdict matched at both boundaries — FAIL `20.19.5, 21.7.3, 22.12.0, 22.22.0, 22.22.1, 23.11.1, 24.0.0, 24.14.0, 25.5.0`; OK `22.22.2, 24.15.0, 26.0.0, 26.10.0`. The binding constraint is `^22.22.2 || ^24.15.0 || >=26.0.0`, declared by `jsdom@30.1.1` and three transitives (`@asamuzakjp/css-color`, `@asamuzakjp/dom-selector`, `w3c-xmlserializer`); `react-router@8.4.0`'s `>=22.22.0` is real but looser at the 22.x boundary, and `vitest` is what excludes the odd-numbered lines. The old floor was never exercised because this machine runs Node 26.10.0, which satisfies everything.

Section 6 now prescribes `server.forward-headers-strategy=native` rather than treating `framework` as equivalent, and names `server.tomcat.remoteip.internal-proxies`. `framework` (`ForwardedHeaderFilter`) has no trusted-proxy notion and believes `X-Forwarded-For` from whatever connects, which hands the rate-limit key back to the client — the exact bypass the section exists to warn about. This was verified **behaviourally**: two runs sending 11 registrations (limit 10/hour per client address) from two different `X-Forwarded-For` values, reading `source.ip_hash` off the resulting 429 audit events. With the proxy outside `internal-proxies` the result was `201×10, 429` then `429×11` with both 429s carrying the **same** `ip_hash` — one shared bucket, header silently ignored, nothing logged. With the proxy trusted, `201×10, 429` per address with two **distinct** hashes. The reviewer then confirmed the mechanism from the jars: the README's nine-entry default list is `internal-proxies`' documented default exactly, `RemoteIpValve`'s `remoteIpHeader` defaults to `X-Forwarded-For` so `native` alone suffices, and the valve has no message key for a non-matching peer, so "fails silently" is accurate.

**Verification steps.** Criterion 2 was run green by the implementer and then **re-run independently by the reviewer**: `./mvnw -P migrations test -Dtest=NonH2MigrationTest` → 2/2, with "Successfully applied 4 migrations" and `ddl-auto=validate` passing per vendor against `postgres:16-alpine` and `mysql:8.0`. Targeted tests only, by request — the full suite was not run: `StartupConfigurationTest`, `DevProfileApiTest`, `ManagementEndpointsTest`, `SessionRestartTest` and `BootstrapAdminTest` → **50 tests, 0 failures, 0 errors** (the tests most exposed to the dependency change). Criterion 3's property audit matched every property token the README names against `application.properties` / `application-dev.properties` or a scanned `@ConfigurationProperties` prefix, with zero unmatched; the documented env-var forms were proven by starting the app in a non-`dev` profile with configuration supplied *only* as environment variables, which came up with `cookie_secure: true` and wrote the `user-provisioning` audit event. From a genuinely clean tree the quick start was then followed verbatim: backend on 8080 with the dev-fallback Bootstrap Admin and its WARN, SPA on 3000, `GET /api/csrf` 200, `/.well-known/security.txt` served, CSP meta `connect-src` pointing at the API origin, `/h2-console` 302, `127.0.0.1:9090/actuator/health` UP, and `POST /api/login` as `admin`/`password` returning 200 with `passwordChangeRequired: true`. Dev artifacts were removed afterwards. The reviewer additionally checked criterion 1 claim by claim against the source (HSTS, `frameOptions().deny()`, `PERMISSIONS_POLICY` identical to `SecurityConfig:49-51`, audit retention `@Min(90)`, `SECURITY_TXT_VALIDITY_DAYS`, the production build's `VITE_*` failure, the CORS `@Pattern`, secret masking in `toString()`) and validated all eight in-page README anchors.

The reviewer assessed it as a nice-to-have, not a Must-fix and not a human decision, recommending a tracked follow-up issue per the issue-18/19 precedent. **No follow-up issue has been opened** — that is left to the user.
