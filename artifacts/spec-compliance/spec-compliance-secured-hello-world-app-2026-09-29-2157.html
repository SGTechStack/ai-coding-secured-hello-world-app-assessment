Risk classification and severity basis

This audit classifies the system as Low Risk (LR). Two reasons: it is a non-production reference application holding only usernames, email addresses and password hashes; and across every control where the catalogued LR and MR levels differ (as-1, as-3, as-7, as-8, lm-4, lm-19, ck-1, ck-2) the LR level is the higher of the two, so choosing LR cannot under-call a severity.

IM8 Reform — Application Security (as)

ControlVerdictReason
as-1AUTO-FIXOnly the password policy (length ≥ 12) and uniqueness conflicts are specified. No validation contract for email format, username charset/length, or request-body shape. Tighten ticket 05 to require Bean Validation on every request DTO and a matching frontend schema.
as-2AUTO-FIXSpring Data JPA parameterises derived queries, but the Spec never prohibits concatenated JPQL or nativeQuery string building. Add the prohibition to ticket 01 so the audit has something to cite.
as-3AUTO-FIXGET /api/hello returns "Hello, <username>", reflecting stored user input. React escapes by default but that reliance is undocumented. State it, ban dangerouslySetInnerHTML, and constrain the username charset at registration.
as-4AUTO-FIXLogin is well covered — account lockout after 5 failures with a 15-minute cooldown (11) plus IP-level throttling that is independent of account state (12). The control says all authentication mechanisms; password-reset-request and confirm are unthrottled, making them an enumeration and mail-flood vector.
as-5AUTO-FIXLength ≥ 12 is defined; complexity is not. Resolve toward NIST SP 800-63B — keep the length floor, add a breached-password denylist, and explicitly reject composition rules — rather than bolting on character-class requirements.
as-6PASSBCrypt via BCryptPasswordEncoder, no custom hashing, plaintext never logged or stored, hashes never returned in API responses. The catalogue names Argon2/scrypt as examples but BCryptPasswordEncoder is an accepted implementation, so the PRD's mandate is compliant as written.
as-7AUTO-FIX“Role checks enforced server-side via Spring Security; never trusted from client-supplied state” is the right principle, and ticket 17 enforces it on admin endpoints. Missing: an explicit anyRequest().authenticated() default-deny, so a future endpoint added outside the matcher list fails closed rather than open.
as-8AUTO-FIXTicket 16 already does the important part — no default, no committed password, fail fast if absent, never logged. Tighten to name environment variables as the dev mechanism and a managed secret store as the deployment requirement, since “supplied via configuration” would also permit a committed properties file.
as-9AUTO-FIXTicket 01's “security response headers” is a category, not this control. CSP needs named directives. Specify default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self' with no unsafe-inline in the production build.
as-10AUTO-FIXLevel 2 control, so a FAIL here would be Critical — avoided only because the PRD explicitly addresses transport: “Any real deployment must sit behind HTTPS (required for Secure cookies and HSTS).” That is acknowledgement, not a requirement. Require the header in the prod profile with max-age=31536000; includeSubDomains.
as-11AUTO-FIXStrong coverage — session-fixation protection, invalidation on logout (09) and on password reset (14), HttpOnly/Secure/SameSite, plus idle and absolute timeouts (10). The control requires a defined threshold and the Spec names no value. Pin 30-minute idle and 8-hour absolute.
as-12N/ANo file upload capability anywhere in the PRD — no multipart endpoint, no upload field in any story, no binary column in the data model. Nothing to scan.
as-13PASSTicket 01 requires sanitised error responses, and the PRD's enumeration-resistance rule already forces generic errors on login and password-reset-request. Implementation must set server.error.include-stacktrace=never and include-message=never, disable the H2 console outside dev, and keep actuator and API-doc endpoints off the public matcher.
as-14AUTO-FIXLevel 2. Password hashing is delegated to Spring Security, which is fine, but ticket 13 generates a reset token without naming a source of randomness. Require java.security.SecureRandom with at least 256 bits of entropy, prohibit java.util.Random and Math.random() for anything security-relevant, and prohibit hand-rolled crypto.
as-15N/ACatalogued N/A. No compromise-detection capability is in scope; the available containment action is admin account disable (19), and forced change after an admin-issued credential is handled under ac-6 rather than here.

ac-2N/A (waived)Applicable but waived. PRD Out of Scope: “Multi-factor authentication (MFA/2FA).” Largest single deviation in the build — see the waiver register above.
ac-3FAILSeverity: High. No deactivation after 90 days of inactivity, and no last_login_at column in the users model to derive it from — created_at cannot substitute. Not covered by any out-of-scope clause. Fix is additive and cheap: one column written on successful login, one scheduled task, one audit event.
ac-4DEFERREDThe reviewable surface exists — ticket 18 lists username, email, role, enabled status and created-at, and the Spec's Roles table is the declared permission baseline. The periodic review cadence is an operational process, not a Spec-phase artefact. Adding last_login_at to the ticket 18 response (from the ac-3 fix) is what makes the review actionable.
ac-6FAILSeverity: High. Story 12 seeds an admin from app.admin.password — an admin-issued credential — and nothing ever forces it to be changed. Ticket 16 solves credential provenance (externalised, fail-fast, unlogged) but not credential rotation. Needs a force_password_change flag, a filter returning 403 PASSWORD_CHANGE_REQUIRED on every endpoint except password-change and logout, a change endpoint requiring the current password and rejecting reuse, and a dedicated frontend page with a route guard.
ac-7N/ANot a government digital service with public users, and not an internal agency system on WOG AAD. Demonstrating a local username/password flow is the declared purpose of the PRD, so a national-identity step-up has no place to attach.
ac-8N/A (waived)SCIM or SSO JIT provisioning presupposes an external identity source to synchronise from, and there is none — accounts are self-registered (Story 1) and admin-managed (Stories 9–11) by design. Follows from the ac-12 waiver.
ac-12N/A (waived)Applicable but waived. The control prohibits local credentials for internal users; local credentials are the entire subject of this build. Defensible for a reference application, blocking if it were ever fielded as an internal agency service. Record in the deviation register.

IM8 Reform — Logging and Monitoring (lm)

ControlVerdictReason
lm-4AUTO-FIXThe PRD's event list is good — login success/failure, lockout, reset requested/completed, and role change/enable/disable/delete with actor and target. It omits one of the three categories the control names: authorization failures. A USER receiving 403 from /api/admin/** is the clearest signal of privilege probing and currently goes unlogged. Add it, plus session-timeout terminations.
lm-15AUTO-FIXLevel 2. “Structured log lines” asserts the property without defining it — no schema, no field set, so nothing is verifiable. Name ECS via Spring Boot's native logging.structured.format.console=ecs and fix the audit field set: timestamp, level, event, actor, target, outcome, source IP, session or correlation id.
lm-16FAILSeverity: Critical (Level 2 control). Latency, traffic, errors and saturation are instrumented nowhere in the Spec, and no ticket among the 24 covers them. The out-of-scope list excludes CI/CD and hosting infrastructure but says nothing about application metrics, so this is an omission rather than a waiver. Actuator plus Micrometer is a small, self-contained addition.
lm-18N/ACatalogued N/A for non-public services. This is a reference application, not a public-facing government digital service, so there is no WOGAA tracking obligation.
lm-19AUTO-FIXLevel 2. “Never log passwords” is covered, and only the token hash is persisted, which is right. But the stubbed EmailService logs the reset link by design (Story 6), and that link carries the live plaintext token — a credential written to a log, which is what this control exists to prevent. Confine it to the dev profile at DEBUG on a dedicated non-audit logger, mask email and username in non-audit logs, redact Cookie and Authorization headers, and record the stub as a deployment-blocking deviation.

ARC Framework — all 88 controls

Framework-level determination: N/A. The ARC Framework governs agentic AI systems. Every one of its 88 controls presupposes at least one of: an LLM, an MCP server or tool-calling surface, an agent system prompt, agent memory, inter-agent messaging, or agent-generated code and queries.

The application under specification is a React frontend and a Spring Boot REST API implementing username/password authentication over Spring Data JPA. It contains no model inference, no LLM dependency, no tool-calling surface, no agent, and no AI-generated output. There is no component for any ARC control to attach to. Scope of this audit

Specification audited: .scratch/secured-hello-world/spec.md together with its source of truth prd/assessment-prd.md, since the spec defers to the PRD on any disagreement. Policy sources: policies/references/im8-reform-app-policy.md (36 controls) and policies/references/arc-framework-policy.md (88 controls). Control risk levels and the severity matrix are taken from the im8-review skill's catalogue; controls without a catalogued level (all of ac, dp, pm, st) default to Level 1.

This is a Spec-phase audit. No code exists yet, so no control is assessed against an implementation — a PASS here means the Specification mandates the control, not that it is built. The im8-review skill performs the code-level audit once an implementation exists, and its stricter evidence standard applies then: a control delegated to a framework without the module being both imported and configured in the application's own code is a WARN, not a PASS.
