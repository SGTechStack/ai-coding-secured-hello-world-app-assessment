# 09: Password reset, end to end

**What to build:** A user who forgot their password can request a reset link by email, and always sees the same "if an account exists…" message. Following the link lets them set a new password. Doing so signs them out everywhere, clears any lockout, and lands them on the login page with "Password updated. Please log in." This ticket also introduces the "expire all sessions for a user" operation that the admin actions (12) reuse. See spec §Backend modules › Password reset and Session registry, §Frontend modules, and Acceptance scenarios › Story 6.

**Blocked by:** 06, 07

**Status:** resolved

- [x] Spring Security's in-memory `SessionRegistry` and the HTTP session event publisher are registered through `sessionManagement` (unlimited concurrent sessions). A single "expire all sessions for user X" operation exists. An expired session's next request gets the JSON `401`, never a redirect.
- [x] `POST /api/v1/auth/password-reset/request` with `{email}` always answers `202` with an empty body, for known, unknown, disabled and malformed emails alike. It is throttled at 10 per IP per 15 minutes.
- [x] For an enabled account only: earlier unused tokens are invalidated, a new 256-bit `SecureRandom` token is created and stored as a SHA-256 hash with a 30-minute TTL (`app.security.password-reset.token-ttl`), and `EmailService.sendPasswordResetEmail` receives `<app.frontend-url>/reset-password#token=<token>`. The stub logs the link on its own non-audit logger, which is the only place a token is ever logged.
- [x] `POST /api/v1/auth/password-reset/confirm` with `{token, newPassword}` and a valid token: the new BCrypt hash is set, the token is marked used, the lockout is cleared, every session of the user is expired, and it answers `204`. The new password works and the old one fails.
- [x] A reused, expired (by the clock), superseded or unknown token → the same `400 INVALID_RESET_TOKEN` "This reset link is invalid or has expired.", with the password unchanged. A policy failure → `400 VALIDATION_FAILED` and doesn't consume the token.
- [x] Audit events `PASSWORD_RESET_REQUESTED` (target `unknown` for unknown emails; the email itself is never logged), `PASSWORD_RESET_COMPLETED` and `PASSWORD_RESET_REJECTED`.
- [x] The login page has a "Forgot password?" link. The `/forgot-password` and `/reset-password` routes are anonymous-only.
- [x] The forgot-password page shows the generic message for any response.
- [x] The reset page reads the token from `location.hash` on mount, removes the hash with `history.replaceState`, and keeps the token in component state only. An invalid token shows the message with a link to `/forgot-password`. Success navigates to `/login` with the notice. The in-memory CSRF token is dropped after a successful confirm.
- [x] e2e Story 6, scenarios 1–4, passes under the CSP fixture, using freshly registered users. The ticket's Comments record how the e2e reads the reset link (backend log capture or a dev-only hook).

## Comments

- **Session expiry (reuse in 12).** `security.SessionExpiry` (public `@Component`) has `expireAllSessionsOf(String username)`: pass the stored (lowercase) username. It marks every session of that principal in the `SessionRegistry` expired; the session actually ends on its next request, when `ConcurrentSessionFilter` invalidates it, expires `JSESSIONID` and answers the JSON `401 UNAUTHORIZED` (`JsonSecurityErrorHandler` is also the `SessionInformationExpiredStrategy`). That ending is deliberately **not** audited as `LOGOUT`: an object post-processor replaces the filter's logout handlers with plain invalidate + cookie clearing. Registry is in memory, this instance only (no Spring Session).
- **Registration of sessions.** `SessionRegistryImpl` and `HttpSessionEventPublisher` are beans; `sessionManagement().sessionConcurrency(maximumSessions(-1), sessionRegistry, expiredSessionStrategy)`. Because REST login runs the `sessionAuthenticationStrategy` bean itself, that bean now also contains `RegisterSessionAuthenticationStrategy` (after the fixation strategy, so the *new* session id is registered). MockMvc sessions register too (MockHttpSession ids), but session-destroyed events only fire in a real container, so `SessionExpiryHttpTest` (RANDOM_PORT) covers the container path, including the expired cookie.
- **Package `passwordreset`.** `PasswordReset` service (`request`, `confirm`), `PasswordResetController` (`/api/v1/auth/password-reset/{request,confirm}`), entity `PasswordResetToken` (`token_hash` mapped as `CHAR` via `@JdbcTypeCode`), `EmailService` + `LoggingEmailService` (logger `EMAIL`, INFO, link in the message text so it is readable in the plain dev console and ECS). Token: 32 `SecureRandom` bytes, Base64url without padding (43 chars); stored as lowercase SHA-256 hex. Expiry is `now >= expires_at` on the injected `Clock`. Consuming a token is one conditional `UPDATE ... WHERE used_at IS NULL`, so two concurrent confirms can't both win. A new request marks older unused tokens used.
- **Request.** `{email}` is not validated at all (malformed, empty or missing email → `202` too); only unparseable JSON is `400 MALFORMED_REQUEST`. Throttle `passwordResetRequestThrottle` (`app.security.throttle.password-reset-request`, 10/15 min) is acquired first, every request counts, refusal is `429` + `REQUEST_THROTTLED endpoint=password-reset-request`. Known-but-disabled accounts get no email.
- **Confirm.** `newPassword` carries `@AcceptablePassword`, so a policy failure is a `400 VALIDATION_FAILED` (`fieldErrors[newPassword]`) before the token is looked at, and the token stays usable. A missing token is `INVALID_RESET_TOKEN`. Success calls `UserAccount.resetPassword(hash)`, which uses ticket 08's `clearLockout()` (merged `feat/secure-auth` into this branch), then `SessionExpiry`.
- **Audit.** `PASSWORD_RESET_REQUESTED` (`actor=anonymous`, `target=<username>` or `unknown`; the submitted email is never logged), `PASSWORD_RESET_COMPLETED` (`actor=<username>`), `PASSWORD_RESET_REJECTED` (`actor=anonymous`, `target=<username>` when the token was known but used/expired/superseded, else `unknown`).
- **Config.** `app.frontend-url` is required (validated http(s) URL, trailing slash trimmed) and `app.security.password-reset.token-ttl` (30m) must be positive, both bound by `PasswordResetProperties` (prefix `app`). Only dev and test default the URL (`http://localhost:3000`); prod needs `APP_FRONTEND_URL` or startup fails. `ProdProfileTest`, `CorsStartupTest` and `AdminBootstrapStartupTest` now pass `app.frontend-url`; any later prod-context test must too.
- **Backend tests.** `PasswordResetApiTest` (14 cases, clock-controlled, unique users/IPs) reads links from captured output of the real stub instead of a test `EmailService`, which also proves the stub is the only place the token appears. The disabled-account case disables via `JdbcTemplate` (no admin API yet); ticket 12 may switch it to the API. `SpaAuthFlow.withCsrf`, `loginRequest` and `freshCsrfCookie` are now public.
- **Frontend.** `requestPasswordReset(email)` and `confirmPasswordReset(token, newPassword)` in `api/auth.ts` (403 retry; confirm calls `dropCsrfToken()` on success). `apiRequest` resolves an empty `202` like `204`. `LOGIN_NOTICES["password-updated"]`. Routes `/forgot-password` and `/reset-password` use `requireNoSession`. The forgot page shows the generic message for any HTTP answer (202, 4xx incl. 429, 5xx); only a request with no answer at all shows "Unable to connect". The reset page reads the token once from the router location's hash (the browser's `location.hash`) in a `useState` initialiser (StrictMode-safe) and removes it with `router.history.replace(pathname)`, which is `history.replaceState` in the browser and keeps the router in sync; no token at all shows the invalid-link message immediately.
- **E2E: reading the reset link.** Backend log capture, no dev-only hook: the e2e backend `webServer` gets `LOGGING_FILE_NAME=backend/target/e2e-backend-<BACKEND_PORT>.log` (path exported to workers as `E2E_BACKEND_LOG` from `playwright.config.ts`), and `resetLinkFor(email)` in `e2e/support.ts` polls that file for the newest `Password reset email to <email>: <link>` line. The backend also gets `APP_FRONTEND_URL=http://localhost:<FRONTEND_PORT>` and `APP_SECURITY_THROTTLE_PASSWORD_RESET_REQUEST_MAX_ATTEMPTS=1000`. A backend reused locally (`reuseExistingServer`) must have been started with the same env, or the link is never found. Scenario 4's second browser is `browser.newContext()`, outside the CSP fixture's `context`. Suite: 31 passed with `CI=1 BACKEND_PORT=18089 FRONTEND_PORT=13009`, and Story 6 passed 3 repeats.
- **Review fix (S3): reset-request timing.** The request did the token work and the synchronous email only for a known, enabled account, so the response time could reveal who has an account (spec A06). Now the request thread does the same for every email: one lookup (for the audit `target`), the `PASSWORD_RESET_REQUESTED` line, then a hand-off to Spring Boot's application `TaskExecutor` (`applicationTaskExecutor`). The task looks the account up again, supersedes old tokens and stores the new one in its own `TransactionTemplate` transaction, and emails the link only after that commits, so a link never arrives before it works. A failure there is logged (`ERROR`, no email or token); the requester already has their `202`. We chose this over padding to a fixed delay because padding still leaks under load and slows every request. The tests that read the link now wait for it (Awaitility, already on the test classpath), and `PasswordResetApiTest.theLinkIsIssuedAndEmailedOffTheRequestThread` shows the email line comes from another thread than the request's audit line. The e2e `resetLinkFor` already polled the log, so it needed no change.
- **Review fix (T5): confirm signs out after commit.** `confirm` now uses `SessionExpiry.expireAllSessionsOnCommit`, as the admin actions do: sessions end and `PASSWORD_RESET_COMPLETED` is logged only once the new hash is committed. Responses are unchanged.
