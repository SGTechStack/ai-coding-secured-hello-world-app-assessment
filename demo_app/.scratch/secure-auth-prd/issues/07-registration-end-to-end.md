# 07: Registration, end to end

**What to build:** A visitor can create an account from a "Create an account" link on the login page. They get clear field errors, including "username already taken", then land on the login page with "Account created. Please log in." Nobody can register as an admin, weak passwords are rejected, and anything typed into the first name is shown as text, never run. See spec §User Stories › Registration, §Backend modules › Password policy and Registration, §Frontend modules, and Acceptance scenarios › Story 4.

**Blocked by:** 02, 04, 05, 06

**Status:** resolved

- [x] A shared password policy component checks 12–64 characters, ≤72 UTF-8 bytes and a bundled top-10k common-password list (case-insensitive). It has no composition rules and never echoes the password back.
- [x] `POST /api/v1/auth/register` is anonymous and CSRF-protected, with body `{username, email, firstName, password}` validated as the spec describes. Username and email are normalised to lowercase.
- [x] Success → `201` with the new `UserProfile` and **no session** created. The new user can then log in.
- [x] `"role": "ADMIN"` or `"enabled"` in the body has no effect: the account is `USER` and enabled.
- [x] A taken username or email (case-insensitive) → `409 ACCOUNT_CONFLICT` with `fieldErrors` naming the field(s). A short, common or >72-byte password → `400 VALIDATION_FAILED` naming `password`.
- [x] An HTML or script payload in `firstName` is stored and returned verbatim as JSON.
- [x] Registration allows at most 10 requests per IP per 15 minutes, then answers `429` using the limiter from 06.
- [x] A `USER_REGISTERED` audit event is emitted. The plaintext password never appears in captured logs.
- [x] A `/register` route, anonymous-only (a signed-in user is redirected to `/`), with username, email, first name, password and confirm password fields. It validates on submit using `FormField`, catches a mismatched confirmation, maps server `fieldErrors` onto fields, and announces errors to screen readers.
- [x] The login page has a "Create an account" link and shows a one-shot notice from a typed, fixed-enum search param, never free text.
- [x] Frontend XSS test: with a `firstName` of `<img src=x onerror=alert(1)>`, the landing page shows the literal text and renders no `img`.
- [x] e2e Story 4, scenarios 1–4, passes under the CSP fixture.

## Comments

- **Password policy (reuse in 09 and 10).** `user.PasswordPolicy` (`@Component`) has `Optional<String> problem(String password)`: empty when acceptable, else a fixed message that never contains the password (`null` fails with the length message). Rules: 12–64 code points (an emoji counts once), ≤72 UTF-8 bytes, not on `src/main/resources/security/common-passwords.txt` (SecLists top-10k, MIT, attribution in its `#` header), compared lower-cased. On a request DTO, annotate the field with `@AcceptablePassword` (e.g. 09's `newPassword`): its validator is built by Spring with the policy injected, and reports the policy's message as that field's `fieldErrors` entry. The bootstrap (10) should call `problem(...)` directly for a clear startup message.
- **Account creation (reuse in 10).** `user.AccountRegistration.register(NewAccount, Role)` is the one way to create an account: normalises username (`UserAccount.normaliseUsername`) and email (`UserAccount.normaliseEmail`: strip + lowercase), checks the policy (throws `400 VALIDATION_FAILED` naming `password`), checks conflicts (throws `409 ACCOUNT_CONFLICT` naming `username` and/or `email`), encodes with the BCrypt bean and sets `created_at` from the `Clock`. The account is enabled with the given role; the controller always passes `Role.USER`. A unique-constraint race is re-checked and reported as the same `409`. `NewAccount` and `RegisterRequest` redact the password in `toString()`. The repository gained `existsByUsername`/`existsByEmail` (normalised values only); 09 adds `findByEmail`, 10 a role lookup.
- **Errors.** New `web.ApiException(status, code, message, fieldErrors)`, rendered by `ApiExceptionHandler` as an `ApiError`. Use it for new codes instead of adding handlers (`INVALID_RESET_TOKEN`, `USER_NOT_FOUND`, `SELF_ACTION_NOT_ALLOWED`). `ApiException.validationFailed(Errors | List<FieldError>)` gives `400 VALIDATION_FAILED` with message `"Some fields are invalid"` and one `fieldErrors` entry per field, sorted by field name (the first violation wins; each DTO field's constraints share one message). The global `MethodArgumentNotValidException` handler now produces that generic shape; login keeps `"Username and password are required"` and no `fieldErrors` through a controller-local `@ExceptionHandler` in `AuthController`.
- **Validation.** `RegisterRequest` trims `email` and `firstName` in its compact constructor, before validation. `firstName` is stored trimmed, otherwise verbatim (HTML included); 1–100 characters, no `\p{Cc}`. Username `[A-Za-z0-9._-]{3,50}`. Email `@Email` + ≤254. No `role`/`enabled` fields; Jackson ignores unknown properties.
- **Throttle.** `registrationThrottle` (`app.security.throttle.registration`, 10 per 15 min) is acquired before the body's validation errors are reported (the controller takes a `BindingResult`), so every request counts, including `400`s and `409`s; a refused request is `429` and audited `REQUEST_THROTTLED` with `actor=anonymous` and `endpoint=register`. Malformed JSON (`400 MALFORMED_REQUEST`) fails before the controller and doesn't count. 09's reset-request throttle can follow the same pattern (`endpoint=password-reset-request`).
- **Audit.** `USER_REGISTERED` with the new (lowercase) username as actor. Conflicts and validation failures aren't audited (only the throttle refusal is).
- **Backend tests.** `RegistrationApiTest` (20 cases). `SpaAuthFlow` gained public `uniqueIp()`, `register(mvc, username, password)` (email `<username>@example.com`, first name `Test`, from a unique IP, expects `201`), `logIn(mvc, username, password)`, `credentialsJson`, `registrationJson`, `registerRequest`. Tests that register users must send from `uniqueIp()` (the helper does), or they share `127.0.0.1`'s registration counter with every other class in the cached context. MockMvc prints a failing request's body (password included) to stdout, so "password never logged" assertions use a password unique to the test.
- **Frontend.** `register(Registration)` in `api/auth.ts` (403 retry like login; does not drop the CSRF token, as no session is created). `/register` and `/login` share a `requireNoSession` guard in `router.tsx`; 09 can reuse it for `/forgot-password` and `/reset-password`. The login notice lives in `routes/loginNotice.ts`: add `"password-updated": "Password updated. Please log in."` to `LOGIN_NOTICES` and navigate with `search: { notice: "password-updated" }`. Gotcha: TanStack Router merges `validateSearch`'s result over the raw params, so `parseLoginSearch` always returns the `notice` key (possibly `undefined`); omitting it let `?notice=toString` through. The notice is a `role="status"` alert shown until the user submits, and the param is removed from the URL on mount. Errors are announced by focusing the first invalid field after render (`useFocusFirstError`), since `FormField` has no live region. `settleNoSoonerThan` moved to `src/lib/timing.ts`.
- **E2E.** `e2e/story-4-registration.spec.ts` (Scenarios 1–4). `e2e/support.ts` gained `uniqueUser(testInfo, overrides)`, `registrationForm`, `submitRegistration` (waits for the "Create an account" heading first: the login page's "Username" field is otherwise filled mid-navigation), `registerThroughUi`, `logInThroughUi`, `REGISTERED_NOTICE`. Use `getByLabel(..., { exact: true })` on the registration page ("Password" also matches "Confirm password"). The e2e backend gets `APP_SECURITY_THROTTLE_REGISTRATION_MAX_ATTEMPTS=1000`; 08/09 should add the login and reset-request equivalents if their scenarios need them. Suite: 26 passed with `CI=1 BACKEND_PORT=18087 FRONTEND_PORT=13007`, and Story 4 passed 4 repeats in a row.
